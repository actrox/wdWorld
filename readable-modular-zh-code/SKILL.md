# Readable Modular Zh Code

## Overview

这个技能用于把“能运行的代码”提升为“长期可维护的代码”。

它适用于以下任务：

- 用户要求高可读性
- 用户要求模块化设计
- 用户要求中文注释
- 用户要求注释率达到明确阈值
- 用户要求统一编码规范
- 用户提到 `getInstance`、单例、静态工厂、全局入口等容易写乱的模式

## Core Rules

所有实现默认遵守以下规则，除非用户或项目现有规范明确冲突。

### 1. 可读性优先于炫技

- 优先写直白代码，不为“高级感”牺牲理解成本
- 一个函数只做一类事
- 一个模块只承载一个明确职责
- 命名必须表达业务含义，而不是只表达技术动作

### 2. 模块化优先于堆叠

- 拆分复杂逻辑为小函数、小模块
- 避免超长函数、超长类、超长文件
- 输入、处理、输出尽量分层
- 配置、常量、工具函数与业务逻辑分离

### 3. 中文注释必须解释“为什么”

- 注释优先解释设计意图、边界条件、业务规则
- 避免无意义注释，例如“给变量赋值”
- 对复杂分支、兼容逻辑、性能取舍、异常处理必须写中文注释
- 对公共接口、核心类、核心函数写中文文档注释

### 4. 注释率要求

默认目标：注释率不低于 `32%`

执行口径：

- 以“有效实现代码”对应的说明性中文注释为主
- 优先保证关键路径和复杂逻辑有注释，不用靠无意义注释凑数
- 如果项目已有更严格规范，遵循项目规范
- 如果语言生态不适合机械追求 20%，要明确说明并改为“关键模块高注释覆盖”

### 5. 良好编程习惯

- 明确边界条件
- 处理异常而不是忽略异常
- 避免魔法数字和魔法字符串
- 尽量减少隐式共享状态
- 优先纯函数和显式依赖
- 保持输入输出结构清晰
- 新代码要考虑可测试性

## Workflow

### Step 1: 先读上下文，再动代码

- 先理解现有项目风格
- 找出现有模块边界
- 识别重复逻辑、长函数、坏命名、强耦合点
- 不在没有上下文时盲目引入设计模式

### Step 2: 先定结构，再写实现

在开始写代码前，先在心里或回复中明确：

- 入口模块是什么
- 数据流怎么走
- 需要拆成几个函数或类
- 哪些逻辑要独立成工具层
- 哪些地方需要中文注释解释

### Step 3: 编写时遵守分层

优先按以下顺序组织：

1. 常量 / 配置
2. 类型定义
3. 核心公开接口
4. 内部辅助函数
5. 异常处理与收尾逻辑

### Step 4: 完成后自检

至少检查这些问题：

- 变量名是否一眼能懂
- 函数是否过长
- 模块职责是否混乱
- 中文注释是否真的解释了原因
- 是否存在重复逻辑
- 是否存在隐式副作用
- 是否容易写单元测试

## Commenting Standard

以下场景必须优先补中文注释：

- 复杂业务规则
- 特殊边界条件
- 兼容旧行为
- 容易误用的公开接口
- 非直觉的数据转换
- 缓存、并发、懒加载、单例
- 文件、网络、数据库等 I/O 逻辑

以下场景不要写废话注释：

- `i++` 旁边写“i 自增”
- `return result` 旁边写“返回结果”
- 简单 getter / setter 上重复函数名含义

## Naming Standard

- 类名表达对象身份
- 函数名表达动作和结果
- 变量名表达业务语义
- 布尔值使用可判断前缀，例如 `is`、`has`、`can`、`should`
- 避免 `data`、`temp`、`obj`、`util` 这类泛化命名，除非上下文已经足够明确

## Function Design Standard

- 单个函数尽量控制在易读范围
- 超过约 `40` 行的函数要主动评估是否应拆分
- 参数过多时改为对象参数或上下文对象
- 返回值结构尽量稳定
- 能早返回就少嵌套

## Module Design Standard

- 一个文件只围绕一个主题
- 公共 API 和内部实现分开
- 工具函数不要反向依赖业务模块
- 业务模块不要混杂 UI、存储、网络和格式化细节

## getInstance Guidance

知道，`getInstance` 通常是单例模式里暴露全局实例的方法。

但这个方法很容易被写成“随处可取、难测、难替换”的隐式全局依赖，所以要遵守以下规则：

### 何时可以用

- 应用级唯一资源确实只有一个
- 创建成本高，重复构造没有意义
- 生命周期稳定且容易管理

典型例子：

- 配置中心
- 日志管理器
- 本地缓存管理器
- 数据库连接管理入口

### 何时不要用

- 只是为了图省事
- 会让业务层偷偷依赖全局状态
- 需要并发安全却没有正确处理
- 未来很可能需要多实例

### 推荐写法

- `getInstance` 只负责实例获取，不负责堆积业务逻辑
- 初始化逻辑和业务逻辑分离
- 对线程安全、懒加载、释放时机写中文注释
- 优先通过依赖注入传递实例，而不是在深层函数里到处调用 `getInstance`

### 审查 getInstance 时必须检查

- 是否线程安全
- 是否可测试
- 是否隐藏了全局状态副作用
- 是否真的需要单例
- 是否可以改为模块级工厂或依赖注入

## Output Pattern

当用这个技能写代码时，默认输出应满足：

- 先给出清晰实现，不先堆概念
- 代码结构清楚，分层明确
- 中文注释自然、克制、有效
- 关键模块注释充足
- 有必要时说明为什么不用某种“更花哨”的写法

## Review Checklist

交付前默认按以下清单审查：

- 是否具备高可读性
- 是否完成合理模块拆分
- 是否存在超长函数或超长类
- 中文注释是否覆盖关键逻辑
- 注释率是否达到或接近目标要求
- 是否避免了魔法值和模糊命名
- 是否控制了副作用和耦合
- `getInstance` 或类似单例入口是否被谨慎使用

## When To Escalate

遇到这些情况要先说明再继续：

- 用户要求的注释率与项目现有规范冲突
- 现有项目整体风格与本技能差异过大
- 为满足 32% 注释率会明显伤害代码整洁度
- 用户要求使用单例，但实际更适合依赖注入或工厂模式

## Default Behavior

未给出额外约束时，按以下默认策略执行：

- 优先重构为模块化结构
- 默认添加中文注释
- 默认补齐边界处理
- 默认避免滥用单例
- 默认保持实现朴素、稳定、易维护
